# Notes conventions

This wiki is plain markdown with YAML frontmatter. You work with notes; the
organizer owns their long-term structure. These rules exist because structure
that is imposed decays; structure that emerges is maintained.

- **Search before you capture.** Duplicates are how a wiki decays into noise.
  A capture that re-tells an existing note is worse than no capture.

- **Capture goes to the inbox.** New notes land in `00-inbox` and are promoted
  later by the organizer. Filing at capture time is what creates a tangled,
  unmaintainable tree. It is expected for captures to be rough.

- **Prefer appending over rewriting.** `append` keeps what is already there;
  `update` replaces it. Merge new information into an existing note rather
  than replacing it, unless the old content is genuinely wrong.

- **Never delete; archive.** Moving a note to `40-archive` retires it.
  Deleting destroys history the wiki can never recover.

- **Rewrite only with the current revision.** `update` refuses to overwrite a
  note you have not just read. A revision conflict means something else
  changed it — read again and merge; do not force it.

- **Prefer a new note over a longer one.** Small notes about one thing link
  better than large notes about many. When a note covers several subjects,
  split it and link the parts.

- **Tags are a shared vocabulary.** Reuse existing tags (see `xael://tags`)
  instead of inventing near-synonyms; the organizer consolidates drift.

- **The organizer owns structure.** Renaming, retitling, and link maintenance
  are its job. If you see something misplaced, `move` it — but do not
  restructure folders on your own.

- **Address notes by id, refer to them by title.** Tool calls use the `id`
  from search results. Files themselves are readable slugs.
